## 1. 추진 배경과 목표

### 1.1 해결하려는 문제

- 중앙정부, 경기도, 수원시, 보증기관에 공고가 분산되어 있어 매일 사람이 반복 확인해야 한다.
- 공고 본문보다 HWP·HWPX·PDF 첨부에 실제 자격, 제외업종, 정산조건이 들어 있는 경우가 많다.
- 같은 공고가 여러 기관에 복제되고 정정 공고가 덧붙어 단순 제목 알림만으로는 중복과 변경을 구분하기 어렵다.
- 지원금, 사후정산 보조금, 융자, 보증, 카드한도가 섞이면 실제 받을 수 있는 금액을 잘못 판단할 수 있다.
- 매일 모든 원문을 AI로 요약하면 토큰 비용이 누적되고, 정보가 없는 날에도 불필요한 호출이 발생한다.
- **(v1.1 추가)** 공고를 찾아내도 필요서류 준비 기간이 없어 마감을 알고도 신청하지 못하는 일이 반복된다.

### 1.2 구축 목표

- 공식 RSS·오픈API·공개 목록을 우선 사용하여 신규 공고를 자동 발견한다.
- 공고의 HWP·HWPX·PDF·ZIP 원문을 내려받아 위변조·오류 여부를 확인하고 보관한다.
- 원카샵과 수원별당의 사업장 조건을 분리하여 설명 가능한 규칙으로 1차 선별한다.
- 마감일과 정정 사항을 놓치지 않도록 신규·정정·마감변경 이벤트를 기록한다.
- 정상적인 일일 운영에는 LLM 토큰을 사용하지 않으며, 규칙이 판단하지 못한 공고만 상한이 걸린 검토 대기열에 둔다.
- **(v1.1 추가)** 선별된 공고를 신청 작업대장으로 연결해 실제 신청·정산까지 추적한다.
- **(v1.1 추가)** PC 전원 상태와 무관하게 매일 실행되고, 실행이 멈추면 반드시 알려지도록 한다.

### 1.3 범위와 제외 범위

| 포함 | 제외 |
|---|---|
| 공개 공고 목록·RSS·오픈API 조회 | 로그인 우회, CAPTCHA 자동 처리 |
| 공개 첨부 원문 다운로드와 무결성 확인 | 신청서 자동 제출, 전자서명 |
| 로컬 텍스트 추출·키워드·규칙 판정 | 대출 실행, 카드 발급, 결제 |
| 중복·정정·마감 변경 감지 | 선정 전 계약·구매 자동 실행 |
| 일일 요약·검토 대기열 생성 | 담당기관 문의·이메일 발송의 무승인 실행 |
| 신청 작업대장 상태 추적 | 사용자 승인 없는 상태 변경·제출 완료 처리 |

| 원칙 | 적용 방법 | 개선 효과 |
|---|---|---|
| 공식 경로 우선 | 오픈API → RSS → 공개 HTML 순서 | 화면 변경과 브라우저 자동화 장애 감소 |
| 토큰 0 기본 | 수집·추출·필터·요약표를 규칙 기반으로 처리 | 상시 비용 0, 예측 가능한 운영 |
| 설명 가능한 판정 | 점수와 탈락 사유를 함께 저장 | 왜 알림·제외되었는지 재검토 가능 |
| 원문 보존 | 파일 해시·크기·MIME·URL 기록 | 공고 교체와 오류 페이지 저장을 식별 |
| 사업장 분리 | 원카샵·수원별당 프로필을 별도 설정 | 업력·업종·지역 차이로 인한 오판 감소 |
| 증분 수집 | 마지막 성공 시각 이후만 조회 | 사이트 부담·실행시간·중복 알림 감소 |
| 외부 알림 분리 | 수집 성공 후 별도 알림 단계 실행 | 알림 장애가 수집 원본을 잃게 하지 않음 |
| 사람 승인 경계 | 신청·로그인·지출은 자동화 대상에서 제외 | 재정·법률·인증 사고 예방 |
| **불확실은 통과** | **판단 근거가 부족하면 제외하지 않고 검토대기로 보냄** | **미탐(놓침)을 오탐(과다알림)보다 비싼 오류로 취급** |
| **실패는 시끄럽게** | **성공은 조용히, 실패와 무실행은 반드시 경보** | **조용한 중단을 구조적으로 차단** |

> **판정 철학** 단순 키워드 포함 여부만 쓰지 않고, 지역·업력·업종·지원유형의 필수조건을 먼저 검사한 뒤 점수를 계산한다. 이는 제목에 '소상공인'이 들어가도 실제 대상이 제조 소공인·협동조합·특정 지역인 공고를 잘못 추천하는 문제를 줄인다.

## 3. 목표 시스템 구조

시스템은 수집기, 표준화기, 첨부 처리기, 규칙 엔진, 결과 저장소, 알림기로 분리한다. 어느 한 사이트나 알림 채널이 실패해도 이미 받은 원본과 실행 상태는 보존한다.

1. **Source Adapter** 가 각 공식 사이트에서 공고 ID와 상세 URL을 수집한다.
2. **Normalizer** 가 제목, 기관, 등록일, 접수기간, 지역, 유형을 공통 형식으로 바꾼다.
3. **Attachment Worker** 가 공개 첨부를 내려받고 파일 서명과 SHA-256을 확인한다.
4. **Local Extractor** 가 PDF·HWPX·HWP에서 텍스트를 추출하고 **신뢰도 등급**을 부여한다.
5. **Rule Engine** 이 사업장별 필수조건, 제외조건, 관련도 점수를 계산한다.
6. **Event Detector** 가 신규·정정·첨부교체·마감변경을 구분한다.
7. **Digest Builder** 가 신규와 마감임박 공고를 Markdown·CSV로 작성한다.
8. **Pipeline Sync** 가 P0/P1 공고를 신청 작업대장에 등록한다.
9. **Notifier** 는 승인된 채널이 있을 때만 요약 결과를 전달한다.
10. **Watchdog** 이 실행 기록을 검사해 무실행·연속실패를 경보한다.

| 구성요소 | 입력 | 출력 | LLM 사용 |
|---|---|---|---|
| Source Adapter | 오픈API/RSS/HTML | 공고 후보 ID | 없음 |
| Normalizer | 사이트별 필드 | 공통 메타데이터 | 없음 |
| Attachment Worker | 상세 페이지 | 원문 파일·해시 | 없음 |
| Local Extractor | PDF/HWPX/HWP | 추출 텍스트·신뢰도 등급 | 없음 |
| Rule Engine | 메타데이터·추출문 | 점수·판정 사유 | 없음 |
| Event Detector | 이전 스냅숏 | 신규·정정·마감변경 | 없음 |
| Digest Builder | 판정 결과 | 일일 보고서 | 없음 |
| Pipeline Sync | P0/P1 판정 | 작업대장 행 | 없음 |
| Watchdog | 실행 로그 | 경보 | 없음 |
| Optional Review | 검토 대기 공고 | 조건 해석 메모 | **Tier 1/2만** |

## 4. 수집 대상과 연결 전략

**v1.1 변경**: 표준 REST로 제공되는 공공데이터포털 오픈API를 A등급으로 승격했다. HTML 스크래핑은 화면 구조가 바뀌면 즉시 깨지지만 오픈API는 스키마가 안정적이므로, 같은 정보를 얻을 수 있으면 항상 API를 우선한다.

| 등급 | 출처 | 우선 방식 | 첨부·주의점 |
|---|---|---|---|
| A | 중소벤처기업부 사업공고 | 공식 RSS | 상세 페이지에서 HWP/HWPX/PDF 수집 |
| A | 기업마당 지원사업정보 | 공식 JSON/XML API | 인증키 필요, 공고 ID·신청기간·첨부 경로 제공 |
| **A** | **공공데이터포털 K-Startup 공고 API** | **오픈API** | **v1.0에서 C등급 HTML이었음. 스키마 안정적** |
| **A** | **소상공인시장진흥공단 오픈API** | **오픈API** | **정책자금·지원사업 공고 표준 제공** |
| **A** | **보조금24(정부24) 맞춤서비스 목록** | **오픈API** | **사업자 조건 기반 필터링에 직접 활용 가능** |

| B | 경기도시장상권진흥원·경기바로 | 공개 HTML | 상세 페이지별 첨부 파서 필요 |
| B | 경기신용보증재단 | 공개 HTML | 세션·Referer 유지가 필요한 첨부가 있을 수 있음 |
| B | 소상공인24·정책자금 | 공개 공고·공식 원문 | 로그인 화면은 수집하지 않고 공식 공고로 보완 |

> 조달 공고(나라장터)는 지원사업이 아니므로 수집 범위에서 제외한다.

### 4.1 사이트 어댑터 공통 규격

```
adapter.fetch_index(since)          -> [notice_stub]
adapter.fetch_detail(notice_stub)   -> notice_detail
adapter.list_attachments(detail)    -> [attachment_ref]
adapter.health_check()              -> status

필수 필드: source_code, notice_id, title, detail_url, published_at
권장 필드: apply_start, apply_end, organization, region, category
```

- HTTP 요청은 기관별 1~2초 간격을 두고 User-Agent와 타임아웃을 명시한다.
- ETag와 Last-Modified가 제공되면 조건부 요청을 사용해 불필요한 다운로드를 줄인다.
- 목록 1페이지에서 마지막으로 본 공고 ID가 나오면 추가 페이지 조회를 중단한다.
- 로그인이나 보안 검증이 필요한 화면은 실패로 기록하고 다른 비공식 경로로 우회하지 않는다.

### 4.2 해외 IP 접근성 사전 검증 (v1.1 신설)

GitHub Actions 러너는 해외에 위치하므로, 일부 공공기관이 해외 IP를 차단할 수 있다.

- 구축 0단계에서 **소스별 해외 접근성 실측표**를 작성한다(HTTP 상태·응답시간·차단 여부).
- 차단이 확인된 소스는 `sources.yaml` 에 `runner: self-hosted` 로 표시해 국내 PC 러너로 라우팅한다.
- 하나의 소스가 차단되어도 나머지 소스의 수집과 일일 보고서는 정상 생성되어야 한다.

## 5. 데이터 모델과 중복·정정 감지

| 테이블/파일 | 핵심 키 | 역할 |
|---|---|---|
| `sources` | source_code | 기관 URL, 방식, 실행 주기, 러너 위치, 상태 |
| `notices` | source_code + notice_id | 공고 제목·기관·접수기간·원문 URL |
| `attachments` | notice_key + file_id/url | 파일명·크기·MIME·SHA-256·저장경로·**추출 신뢰도** |
| `events` | event_id | 신규·정정·첨부교체·마감변경 이력 |
| `business_profiles` | business_code | 원카샵·수원별당 조건 |
| `assessments` | notice_key + business_code | 필수조건·점수·판정 사유·**규칙 버전** |
| `runs` | run_id | 실행시각·성공/실패·처리건수·오류 |
| **`clusters`** | cluster_id | **복제 공고 묶음과 기준 출처** |
| **`applications`** | application_id | **신청 작업대장 상태머신** |
| **`documents_owned`** | document_code | **보유서류 대장(발급일·유효기간)** |

### 5.1 이벤트 판정 규칙

- `source_code + notice_id` 가 없으면 신규 공고로 기록한다.
- 동일 공고의 본문 정규화 해시가 바뀌면 정정 후보로 기록한다.
- 첨부 URL이 같아도 SHA-256이 바뀌면 첨부 교체로 기록한다.
- 접수 종료일 또는 종료시각이 달라지면 마감변경 이벤트를 별도로 만든다.

### 5.2 복제 공고 클러스터링 알고리즘 (v1.1 신설)

v1.0은 "유사도로 묶되"라고만 기술해 구현이 불가능했다. 토큰 0으로 계산 가능한 구체 규칙을 정의한다.

**1단계 — 제목 정규화**
공백·괄호·대괄호 제거, 연도(`2026년`)·차수(`제3차`, `2차`)·수식어(`(수정)`, `(재공고)`, `(연장)`) 제거, 조사 제거 후 형태소 없이 2-gram 토큰화.

**2단계 — 클러스터 판정**
아래 세 조건을 **모두** 만족하면 동일 클러스터로 묶는다.

| 조건 | 임계값 |
|---|---|
| 정규화 제목의 토큰 자카드 유사도 | ≥ 0.85 |
| 접수기간 겹침 | 하루 이상 겹침 |
| 지역 필드 | 일치 또는 한쪽이 전국 |

**3단계 — 기준 출처 선택**
원기관(주관기관) > 광역지자체 > 기업마당 등 취합 포털 순으로 기준 출처를 정한다. 기업마당 사본은 클러스터의 참조 링크로만 남기고 알림·판정은 기준 출처 기준으로 1회만 수행한다.

**4단계 — 안전장치**
자카드 0.70~0.85 구간은 "묶음 후보"로만 기록하고 자동 병합하지 않는다. 주간 점검에서 사람이 확인한다. 잘못 병합하면 서로 다른 공고 하나를 통째로 놓치므로, 애매하면 병합하지 않는 쪽이 안전하다.

## 6. 첨부파일 수집과 로컬 문서 처리

| 형식 | 검증 | 텍스트 처리 | 실패 시 |
|---|---|---|---|
| PDF | 헤더 `%PDF-` | 로컬 PDF 텍스트 추출 | 스캔 PDF면 OCR 대기열 |
| HWPX | ZIP 서명·내부 XML | 압축 해제 후 section XML 추출 | 원본 보존 후 오류 기록 |
| HWP | OLE 서명 `D0 CF 11 E0` | 로컬 HWP 파서 또는 변환기 | 원본 보존, 수동 검토 표시 |
| ZIP | ZIP 서명 | 안전한 목록 조회 후 허용 형식만 처리 | 자동 압축해제 제한 |
| 기타/HTML | MIME·서명 불일치 | 문서로 처리하지 않음 | 다운로드 오류로 격리 |

### 6.1 보안·안정성

- 확장자만 믿지 않고 MIME, 파일 서명, 크기를 함께 검사한다.
- ZIP은 경로 탈출(Zip Slip), 과도한 압축비율, 실행파일을 차단한다.
- 파일명은 금지문자와 경로 문자를 제거하고 원래 이름은 메타데이터에 보존한다.
- 다운로드 최대 크기와 타임아웃을 설정해 비정상 응답으로 인한 디스크 고갈을 막는다.
- OCR은 CPU 사용량이 크므로 일일 본 수집과 분리하고 필요한 파일만 후처리한다.

### 6.2 추출 신뢰도 등급 (v1.1 신설)

v1.0은 "로컬 HWP 파서 또는 변환기"로만 기술했으나, 실제로는 형식별 추출 품질 차이가 크다. 특히 HWP 5.0(OLE)은 표 안의 텍스트가 자주 유실되는데, **자격요건과 제외업종은 대부분 표 안에 있다.** 추출이 덜 된 문서를 규칙엔진이 "조건 없음"으로 읽으면 조용한 미탐이 발생한다.

| 등급 | 조건 | 규칙엔진 처리 |
|---|---|---|
| **A** | HWPX 또는 텍스트레이어 PDF에서 본문·표 모두 추출, 추출 문자수 ≥ 1,000 | 정상 판정(제외 판정 허용) |
| **B** | 본문은 추출되나 표 구조 유실 의심, 또는 추출 문자수 200~1,000 | 판정하되 다이제스트에 "부분추출" 표시 |
| **C** | 추출 실패, 스캔 PDF, 추출 문자수 < 200 | **절대 '제외'로 판정하지 않고 반드시 '검토대기'로 보냄** |

**처리 우선순위**: HWPX > 텍스트레이어 PDF > HWP(OLE) > 스캔 PDF(OCR 후처리 큐)

같은 공고에 HWP와 PDF가 함께 첨부된 경우가 많으므로, **동일 공고의 여러 첨부 중 가장 높은 등급의 추출문을 판정에 사용**한다.

## 7. 사업장별 규칙 엔진

규칙은 코드에 고정하지 않고 YAML 또는 JSON 설정으로 관리한다. 사업장 사실이 바뀌면 프로필만 수정하며, 과거 판정에는 당시 사용한 규칙 버전을 남긴다.

| 판정 단계 | 예시 | 결과 |
|---|---|---|
| 필수조건 | 경기/수원 소재, 개인사업자, 소상공인 | 불일치 시 제외 |
| 업력조건 | 공고일 기준 2개월·1년·3년 이상 | 확인 불가 시 검토 대기 |
| 업종조건 | 음식점 허용, 제조 소공인 한정 | 허용·제외·검토 |
| 지원유형 | 바우처·사후정산·융자·보증 | 유형별 별도 표시 |
| 비용 적합성 | 간판·인테리어·냉난방·고용 | 필요 지출과 맞으면 가점 |
| 위험조건 | 선정 전 지출 불인정, 자부담, 중복수혜 | 경고 또는 사용자 확인 |

### 7.1 설명 가능한 점수

```
기본점수 0
+4  지역 완전 일치
+3  업종·사업 목적 일치
+2  신청 가능한 지원유형
+2  실제 예정 지출과 일치
+1  마감까지 14일 이상
-5  업력·매출·근로자 조건 미확인

즉시 제외: 지역·업종·사업자 유형의 명백한 불일치
          (단, 추출 신뢰도 C인 문서에는 적용하지 않음)

P0    : 8점 이상 + 필수조건 확인
P1    : 5~7점 또는 일부 확인 필요
검토  : 텍스트 추출 실패·조건 모호
제외  : 필수조건 불일치
```

> **중요** 점수는 선정 가능성을 예측하는 모델이 아니라 검토 우선순위를 정하는 도구다. 실제 자격과 지원금액은 공식 공고문과 담당기관 확인이 기준이다.

### 7.2 미탐 방지 원칙 (v1.1 신설)

**놓치는 오류가 과다 알림보다 비싸다.** 다음 경우에는 점수와 무관하게 '제외'를 금지하고 '검토대기'로 보낸다.

- 추출 신뢰도 C인 문서
- 지역 필드를 파싱하지 못한 공고
- 지원유형을 분류하지 못한 공고
- 기존 클러스터 어디에도 속하지 않으면서 규칙 사전에 없는 새로운 용어가 제목에 포함된 공고

### 7.3 규칙 피드백 루프 (v1.1 신설)

v1.0의 규칙엔진은 정적이라 오탐·미탐이 시간이 지나도 개선되지 않는다.

1. 일일 다이제스트의 각 항목에 피드백 표시란을 둔다: `놓칠 뻔함` / `불필요함` / `정확함`
2. 사용자가 남긴 표시는 `feedback.yaml` 에 공고 키·사유와 함께 누적된다.
3. 주간 점검에서 누적 피드백을 검토해 키워드 사전·가중치·제외 규칙을 갱신하고 규칙 버전을 올린다.
4. 규칙 버전이 올라가면 최근 30일 공고를 신·구 규칙으로 재판정해 **판정이 뒤집힌 건수**를 비교한다. 의도한 변화인지 확인한 뒤 새 규칙을 확정한다.

## 8. 토큰 비용 모델 (v1.1 전면 개정)

### 8.1 왜 "완전 토큰 0"이 아닌가

규칙엔진은 사전에 정의한 조건만 본다. 형식이나 용어가 다른 신규 사업은 규칙이 아예 판단하지 못하고 '검토대기'로 쌓이는데, 검토대기가 매일 쌓이면 사람이 결국 다 읽어야 하므로 자동화의 목적이 사라진다.

따라서 **매일 반복되는 작업에는 토큰을 한 푼도 쓰지 않되, 규칙이 판단에 실패한 소수 공고에만 상한이 걸린 토큰을 쓴다.**

### 8.2 3-Tier 비용 모델

| Tier | 실행 조건 | 입력 범위 | 상한 | 예상 비용 |
|---|---|---|---|---|
| **Tier 0** (상시) | 수집·해시·중복·클러스터링·마감추출·규칙판정·다이제스트·작업대장 동기화 | — | 무제한 | **0** |
| **Tier 1** (조건부) | 규칙이 '검토대기'로 분류한 **신규** 공고만 | 최우선 첨부 추출문의 앞 8,000자 | **일 3건 / 월 예산 상한** | 소액 |
| **Tier 2** (요청 시) | 사용자가 특정 공고를 지목했을 때 | 전체 공고문 | 사용자 판단 | 요청 시에만 |

### 8.3 Tier 1 안전장치

- 하루 3건을 넘는 검토대기 공고는 **점수 순으로 상위 3건만** 호출하고 나머지는 다음 날로 이월한다.
- 월 누적 예산을 초과하면 **자동으로 Tier 0으로 강등**되고, 다이제스트에 "AI 검토 예산 소진, 전량 수동 검토 필요"를 표시한다.
- 이미 Tier 1 검토를 받은 공고는 정정 이벤트가 발생하지 않는 한 재호출하지 않는다(결과를 캐시).
- Tier 1 호출 건수·토큰·비용을 `runs` 테이블에 기록해 매주 점검표에 노출한다.
- Tier 1 결과는 **참고 의견일 뿐 판정 근거가 아니다.** 최종 판정 사유에는 규칙 근거만 남기고 AI 의견은 별도 필드에 보관한다.

### 8.4 완전 토큰 0으로 운영하려면

사용자가 원할 경우 `ai_review.enabled: false` 한 줄로 Tier 1을 끌 수 있다. 이때 검토대기 공고는 전량 사람이 확인하며, 시스템 동작에는 아무 영향이 없다.

## 9. 일일 보고서

### 9.1 보고서 구성

1. **운영 상태 헤더** — 마지막 성공 실행 시각, 소스별 상태, Tier 1 잔여 예산
2. **오늘의 신규 P0/P1** — 사업명, 마감, 지원유형, 관련 사업장, 판정 이유, **부족 서류**
3. **정정·첨부교체** — 바뀐 항목과 이전 값
4. **마감임박** — D-14, D-7, D-3, D-1 구간
5. **검토 대기** — 추출 실패, 조건 모호, Tier 1 이월 건
6. **제외 통계** — 지역 불일치, 제조업 한정, 협동조합 한정 등 사유별 건수
7. **수집 오류** — 사이트명, 오류 유형, 마지막 정상 실행시각

### 9.2 예시 출력

```
■ 운영 상태  마지막 성공 2026-08-01 07:32 | 소스 9/10 정상
             경기신보 연속실패 2회(첨부 403) | Tier1 잔여 예산 82%

[P0 신규] 수원시 소상공인 점포환경 개선
  마감 : 2026-08-14 18:00 (D-13)
  유형 : 사후정산형 보조금 / 자부담 있음
  관련 : 수원별당
  판정 : 수원 소재 + 음식점 허용 + 인테리어 목적 일치 (규칙 v3, 11점)
  추출 : 신뢰도 A (HWPX)
  주의 : 선정 전 지출 인정 여부 확인 필요
  서류 : 사업자등록증 O / 부가세과세표준증명 O / 임대차계약서 △ 갱신필요(2026-08-03 만료)
  원문 : (수집 시 공식 상세 URL 자동 입력)
  첨부 : 공고문.hwpx, 신청서식.hwp
  피드백: [ 놓칠뻔함 / 불필요함 / 정확함 ]
```

### 9.3 필요서류 대조 (v1.1 신설)

마감일을 알아도 서류를 못 맞추면 신청할 수 없다. 공고 추출문에서 서류 요구사항을 규칙으로 뽑아 보유서류 대장과 대조한다.

**필요서류 사전(예시)**: 사업자등록증, 부가가치세 과세표준증명, 소득금액증명, 국세·지방세 완납증명, 임대차계약서, 4대보험 가입자명부, 통장사본, 중소기업확인서, 소상공인확인서

**보유서류 대장(`documents_owned`)** 은 서류별 발급일·유효기간을 관리하고, 다이제스트에서 다음과 같이 표시한다.

| 표시 | 의미 |
|---|---|
| O | 보유 중이며 유효 |
| △ | 보유하나 마감 전 유효기간 만료 → 갱신 필요 |
| X | 미보유 → 발급 소요일 함께 표시 |

발급에 시간이 걸리는 서류가 X인 P0 공고는 **마감 역산 경보**를 띄운다.

## 10. 실행 환경 (v1.1 전면 개정)

### 10.1 v1.0의 문제

v1.0은 1단계 실행환경을 Windows 작업 스케줄러로 지정했다. 그러나 PC가 꺼져 있거나 절전 상태면 그날 수집이 통째로 누락되고, **누락되었다는 사실조차 알 수 없다.** 접수기간이 1~2주인 공고에서는 하루 누락이 곧 기회 상실이다.

### 10.2 권장 구성: GitHub Actions 주 / self-hosted 폴백

| 항목 | 내용 |
|---|---|
| 기본 러너 | GitHub Actions `ubuntu-latest` |
| 비용 | 퍼블릭 저장소 무제한, 프라이빗 2,000분/월. 하루 2회 × 5분 = **약 300분/월** 로 무료 한도 내 |
| 실행 시각 | cron은 UTC 기준이므로 **07:30 KST = `30 22 * * *` (전일), 18:30 KST = `30 9 * * *`** |
| 로그 | 실행 로그 90일 보존, 실패 시 GitHub 알림 |
| 결과 저장 | 저장소 커밋(다이제스트·상태파일) + Drive 동기화(원문·보고서) |
| 시크릿 | GitHub Secrets (오픈API 키, Drive 자격증명) |
| 폴백 | 해외 IP 차단 소스는 집 PC를 **self-hosted runner** 로 등록해 라우팅 |

**동일한 코드가 두 환경에서 그대로 실행된다.** 달라지는 것은 워크플로의 `runs-on` 값뿐이므로, 나중에 전면 PC 실행이나 클라우드 서버로 옮겨도 수집 로직은 수정하지 않는다.

### 10.3 실행 환경 비교

| 방식 | 장점 | 제약 | 권장 시점 |
|---|---|---|---|
| **GitHub Actions** | **PC 무관, 무료, 로그 보존, 시크릿 관리 내장** | **해외 IP 차단 소스 존재 가능** | **1단계 (권장)** |
| Windows 작업 스케줄러 | 국내 IP, 현재 파일체계 재사용 | PC가 켜져 있어야 함, 누락 감지 어려움 | 차단 소스 폴백 |
| 항상 켜진 서버/클라우드 | 국내 IP + 상시 실행 | 비용·키·저장 관리 | 차단 소스가 많을 때 |
| 카카오 업무비서 연계 | 카카오에서 결과 확인 | 자동 완료 푸시 미구현 | 수집기 안정화 후 |

권장 순서는 **Actions 수집 안정화 → Google Drive 결과 동기화 → 승인된 알림 채널 연결**이다. 기존 `drive` 자동화는 사용자 재개 요청 전까지 중지 상태를 유지하고 이 수집기와 별도 작업으로 운영한다.

### 10.4 실행 일정

| 시간 | 작업 | 알림 |
|---|---|---|
| 07:30 KST | 전체 소스의 전일 이후 신규·정정 수집 | P0/P1·마감임박 요약 |
| 18:30 KST | 07:30 이후 증분 수집 | 새 이벤트가 있을 때만 |
| 매일 (수집 후) | **Watchdog 무실행·연속실패 검사** | **이상 시 무조건 알림** |
| 매주 월요일 | 최근 7일 오류·제외·검토대기·피드백 통계 | 운영 점검표 |
| 매월 25일 | 다음 달·분기 공고와 규칙 만료 점검 | 준비서류 갱신 목록 |

## 11. 오류 처리와 운영 관제

### 11.1 오류별 대응

| 오류 | 자동 대응 | 최종 상태 |
|---|---|---|
| 일시적 네트워크 오류 | 지수 백오프 1회 재시도 | 실패 로그 후 다음 실행 |
| 사이트 HTML 구조 변경 | 파서 테스트 실패·해당 소스 중단 | 다른 소스는 계속 수집 |
| 첨부 403/400 | 세션·Referer 조건으로 1회 재시도 | 원문 링크와 오류 보존 |
| 해외 IP 차단 의심 | self-hosted 러너 대상으로 표시 | 다음 실행에서 국내 러너로 |
| 문서 서명 불일치 | 격리 폴더로 이동 | 다운로드 오류 표시 |
| 텍스트 추출 실패 | 원본 보존·신뢰도 C·검토 대기 | 공고 자체는 누락하지 않음 |
| 디스크 부족 | 신규 다운로드 중단 | 긴급 오류 알림 |
| 일일 실행 중복 | 실행 잠금·run_id 확인 | 두 번째 실행 종료 |

### 11.2 데드맨 스위치 (v1.1 신설)

v1.0의 "새 이벤트가 있을 때만 알림" 정책은 **수집기가 죽었을 때도 조용하다.** 조용한 성공과 조용한 죽음을 구분할 수 없다.

- **24시간 내 성공 실행 기록이 없으면 조건 없이 경보**한다.
- 소스별 `마지막 성공 시각`과 `연속 실패 횟수`를 일일 보고서 최상단에 **항상** 노출한다.
- 특정 소스가 **3회 연속 실패**하면 해당 소스를 자동 중단하고 점검 대상으로 표시한다.
- 수집 결과가 0건이어도 각 소스의 HTTP 상태와 마지막 정상 공고 ID를 확인해 **'정상 0건'과 '장애'를 구분**한다.
- 각 실행은 시작·종료시각, 소스별 처리건수, 신규·정정·실패건수, Tier 1 사용량을 남긴다.
- 같은 원인의 실패를 여러 도구로 반복 우회하지 않고 오류 유형과 다음 행동을 한 줄로 기록한다.

## 12. 신청 작업대장과 중복수혜 관리 (v1.1 신설)

v1.0은 수집·선별까지만 다루고, 실제 신청으로 이어지는 과정이 운영절차 6줄로만 존재했다. 공고를 찾아내는 것 자체는 목적이 아니므로 신청 파이프라인을 1급 산출물로 승격한다.

### 12.1 상태머신

```
발견 → 검토 → 서류준비 → 제출 → 결과대기 → 선정 / 미선정 → 정산 → 종결
                ↑                                    │
                └──────── 보류·차기공고 대기 ←────────┘
```

### 12.2 작업대장 필드

| 필드 | 설명 |
|---|---|
| 공고명 / 기관 / 원문 URL | 수집 결과에서 자동 입력 |
| 대상 사업장 | 원카샵 / 수원별당 |
| 상태 | 상태머신 값 |
| 마감일 / D-day | 자동 계산 |
| 지원유형 / 예상 지원액 / 자부담 | 추출문 기반, 사람이 확정 |
| 필요서류 / 부족서류 | §9.3 대조 결과 |
| 담당·다음 행동 / 기한 | 사람이 입력 |
| 제출 증빙 | 접수번호·제출일 |
| 결과 / 정산 마감 | 선정 후 관리 |

### 12.3 운영 원칙

- **자동으로 채우는 것은 '발견' 상태까지만**이다. 그 이후 상태 변경은 사람이 한다.
- 제출 완료는 사용자가 확인했거나 에이전트가 승인받아 제출했을 때만 완료로 기록한다.
- Google Sheets로 두면 휴대폰에서 확인·갱신할 수 있다.

### 12.4 중복수혜 방지

- 이미 선정·수령한 사업 목록(경영안정 바우처 포함)을 사업장 프로필에 유지한다.
- 신규 공고의 추출문에서 중복수혜 제한 조항(`동일 사업 기수혜자 제외`, `당해연도 △△사업 참여자 제외` 등)을 규칙으로 탐지한다.
- 보유 이력과 충돌하면 판정을 자동 제외하지 않고 **"중복수혜 확인 필요" 경고**를 붙여 사람이 판단하게 한다.

## 13. 보안·개인정보·준수

- 수집 대상은 로그인 없이 접근 가능한 공식 공고와 공개 첨부로 제한한다.
- **오픈API 키·Drive 자격증명은 GitHub Secrets에 저장**하고, self-hosted 실행 시에만 Windows 자격증명 저장소를 사용한다. 저장소 코드·로그·커밋에는 절대 기록하지 않는다.
- 수집기 로그와 다이제스트를 커밋하기 전에 시크릿 스캔을 통과시킨다.
- 사업자등록증, 세금증명, 신분정보 같은 신청자료는 공고 수집 폴더와 분리한다.
- 공공기관 이용약관·robots 정책·합리적 요청 간격을 준수한다.
- 외부 이메일 알림을 연결할 경우 업무 전용 계정과 실제 발신 계정을 확인하고, 발송은 별도 승인 범위에서 수행한다.
- 원문은 변경하지 않고, 추출문·판정문은 파생자료임을 표시한다.

### 14.3 필수 시험

- RSS·오픈API 파싱: 신규 1건·기존 1건·잘못된 XML/JSON 입력
- HTML 파싱: 첨부 0개·1개·여러 개·상대 URL
- 파일 검증: 정상 PDF/HWP/HWPX와 HTML 오류페이지 위장 파일
- **추출 신뢰도**: 텍스트 PDF(A), 표 유실 HWP(B), 스캔 PDF(C) 각각 등급이 맞게 매겨지는지
- **신뢰도 C 미탐 방지**: 지역 불일치 문구가 있어도 신뢰도 C면 '제외'되지 않고 '검토대기'가 되는지
- 중복 방지: 같은 공고를 두 번 실행해도 `notices`·`attachments` 가 증가하지 않음
- **클러스터링**: 자카드 0.9 동일공고는 병합, 0.75는 후보로만 기록
- 정정 감지: 동일 ID의 마감일 또는 첨부 해시를 바꿔 이벤트 1건 생성
- 규칙 엔진: 지역 불일치 즉시 제외, 정보 부족은 검토 대기
- **Tier 1 상한**: 검토대기 5건일 때 3건만 호출하고 2건 이월, 예산 초과 시 0건 호출
- **Watchdog**: 성공 기록을 25시간 전으로 조작하면 경보 발생
- 잠금 시험: 같은 시각 두 번 실행해 한 프로세스만 수집
- 장애 격리: 한 사이트 실패 시 다른 사이트 결과와 일일 보고서는 유지

> **개발 환경 제약** 개발 컨테이너에서는 정부 사이트 접근이 차단될 수 있으므로, 어댑터 시험은 **저장된 고정 픽스처(HTML·RSS·JSON·문서 샘플)** 로 오프라인 수행하고, 실 네트워크 검증은 Actions 러너 또는 사용자 PC에서 별도로 실시한다.

## 15. 버전 관리 정책 (v1.1 신설)

문서와 설정이 갱신될 때 **기존 버전을 덮어쓰지 않고 새 버전으로 누적 기록**한다.

| 계층 | 위치 | 역할 |
|---|---|---|
| 원본 | 저장소 `docs/plan/*.md` | Git 커밋 이력이 실제 버전 관리 |
| 배포본 | Drive `11_정부지원_금융` 의 `.docx` | 사람이 읽는 승인본 |
| 이력 | 저장소 `docs/plan/CHANGELOG.md` + 문서 내 개정 이력 표 | 무엇이 왜 바뀌었는지 |

- **파일명 규칙**: `소상공인_정부지원_정책금융_공고_토큰0_자동수집_상세기획안_v{major}.{minor}_{YYYY-MM-DD}.docx`
- **major** = 구조·범위 변경, **minor** = 내용 보완·수치 갱신
- 새 버전은 항상 **새 파일로 업로드**하며 이전 버전 파일은 폴더에 그대로 남긴다.
- 문서 첫 장의 개정 이력 표에 버전·일자·변경요약·근거를 반드시 추가한다.
- 규칙(`rules.yaml`)과 사업장 프로필도 같은 방식으로 버전을 올리고, `assessments` 에 판정 당시 규칙 버전을 남긴다.

## 부록 B. 검증된 사실과 유의사항

- 아래 항목은 **v1.0 작성 시점(2026-07-27) 사용자 환경 기준 확인값**이며, 구축 0단계에서 재검증한다.
  - 중소벤처기업부 사업공고 RSS는 점검에서 HTTP 200과 XML 콘텐츠로 응답했다.
  - 수원시 공고의 공개 HWP 첨부는 로그인 없이 다운로드되었고 실제 HWP OLE 파일 서명과 일치했다.

- 공고 페이지의 공개 여부와 신청 포털의 실제 접수 가능 여부는 다를 수 있으므로 신청 직전에 공식 포털 상태를 다시 확인한다.
- 이 문서는 수집 시스템 기획안이며 개별 지원사업의 선정, 대출 승인 또는 지원금 수령을 보장하지 않는다.
